## 2. Cas limites

| Constat | Référence | Gravité | Proposition |
|---|---|---|---|
| **Identité du même contributeur à travers plusieurs emails et deux fournisseurs** : la règle dit « Un auteur est identifié par son email **ou** son identité fournisseur » (disjonctif) et la table `authors` porte deux clés (email ; provider+external_id) sans identifiant canonique de personne. Une même personne peut être comptée plusieurs fois : bus factor, part des commits et chaîne de validation faussés | §7 « Périmètre multi-dépôts » ; table `authors` (§8) ; REQ-SOC-14 ; REQ-EQ-01..03 | majeure | Trancher le modèle d'identité : une entité `persons` canonique, rapprochement des commits (email) vers les identités MR (external_id) avec fusion dédupliquée et règles départagées ; un test sur un contributeur avec 2 emails + comptes GitHub et GitLab |
| **Même contribution présente dans deux dépôts** (fork synchronisé, dépôt miroir + dépôt principal, cherry-picks) : la règle « sans double comptage » est définie *par dépôt* : le total « tous les dépôts » est la somme des totaux par dépôt et compte la contribution deux fois | REQ-SOC-14 ; §14 « Un commit n'est compté qu'une fois » ; §16 « Métriques multi-dépôts erronées » | majeure | Définir la sémantique d'agrégation « tous » : déduplication par `sha` hors dépôts forks déclarés ; sinon afficher le dépôt d'origine ; un test de non-double-comptage sur un commit présent dans 2 dépôts |
| **Feature/tâche à cheval sur plusieurs dépôts** : `features.primary_repository_id` et `tasks.repository_id` sont nullables, aucun mécanisme d'attribution multi-dépôt ; à quel dépôt rattacher les gate_runs, revues et effets d'équipe d'une tâche qui change deux dépôts ? | Tables `features` et `tasks` (§8) ; REQ-FEA-01 ; REQ-GAT-10 run par `repository_id` nullable | majeure | Trancher : soit interdiction explicite (tâche mono-dépôt, la feature devient multi et ses métriques sont par dépôt), soit table d'association `task_repositories` ; définir l'effet sur les vues Gates organisées par feature |
| **Purge pendant ingestion ou pendant un run de gate** : la purge supprime des lignes pendant qu'une ingestion les réingère, ou pendant qu'un gate utilise un finding/commit daté de > 12 mois ; seule la file d'ingestion est décrite, pas la coordination de la purge | §7 « Rétention » ; §8 « un seul écrivain, file locale » ; REQ-SOC-09 | majeure | Exigence : purge exécutée par la même file unique, la purge attend la fin des ingérations ; un test de purge pendant une ingestion ; purge journalisée avec le nombre de lignes supprimées par table |
| **Purge de l'audit à 12 mois casse la chaîne de hachage** : la rétention par défaut purge l'audit, mais la chaîne `hash = sha256(prev_hash + payload)` doit détecter les ruptures — après purge, chaque audit suivant rompt la continuité et l'audit « inviolable » (REQ-GEN-04 MUST) devient invérifiable | §8 `audit_events` ; §7 « Rétention » (« audit » dans la liste) ; REQ-GEN-04 | majeure | Trancher : soit l'audit est **exclus par défaut de la purge** (conservation illimitée, volume faible d'usage local), soit la purge d'audit sectionne la chaîne sur un ancre annuel (nouveau point de départ haché, documenté et audité) ; scénario de contrôle d'intégrité après purge |
| **`not_run` vs tier 2** : la règle « `not_run` sur un langage présent = `fail` » impose-t-elle la couverture pour SQL/shell (tier 2 « tests + SCA, sans couverture » selon la maquette) ? La portée du `not_run` (par gate, par langage, par tier) n'est pas tranchée — tout dépôt contenant du SQL ou du shell échoue au gate couverture | §7 « Verdict de gate » ; REQ-GAT-08 ; maquette « Tier 2 = tests + SCA, sans couverture » ; §2 « 0 gate `not_run` sur un langage présent » | majeure | Préciser : « not_run = fail » s'applique **par contrôle attendu pour le tier du langage** ; un contrôle hors périmètre du tier est `not_applicable` avec justification ; scénario sur dépôt Ruby + SQL/shell |
| Dépassement des bornes cibles (> 100 k commits, > 5 dépôts, > 50 k findings) : aucun comportement spécifié (perf, pagination, message) | §3.3 « Volume cible » ; §10 Performance | mineure | Une exigence SHOULD : à la limite, avertissement explicite dans l'UI (dépôt volumineux, mesures prêtes) ; dégradation gracieuse documentée |

## 3. Gestion des erreurs

| Constat | Référence | Gravité | Proposition |
|---|---|---|---|
| **Annulation d'un run : mécanisme non spécifié.** `task_runs.pid` et `cancel_requested` existent, mais les agents lancent des processus fils ; tuer seulement `pid` laisse des orphelins. Une terminaison par groupe de processus (session/process-group, kill tree), confirmée sous toutes les plateformes, est requise | REQ-AGT-07 ; table `task_runs` (§8) ; §13 livrable 7 « runner d'agents » | majeure | Spécifier : lancement dans un groupe de sessions/processus dédié, annulation = signal au groupe, statut terminal confirmé, nettoyage des fichiers temporaires ; un test de fuite de processus |
| **Plafond de coût non garanti** : le critère « son coût ne dépasse pas le budget » n'est pas implémentable tel que le coût réel n'est connu qu'à la fin d'un appel (fournisseurs) ; le budget de type coût peut être dépassé d'un tick avant annulation | REQ-AGT-07 ; §14 « Et son coût ne dépasse pas le budget » ; §8 `cost_eur` nullable | majeure | Reformuler le critère : budget contraignant = arrêt du run au plafond établi par estimation cumulée des tokens ; à la fin, afficher « coût réel X € / budget Y € » et signalé si dépassé ; jamais silencieux |
| **Quota et mode fichier non exigés** pour l'ingestion MR : cache/ETag/backoff et « mode fichier » figurent dans les *risques*, pas dans les exigences REQ-* — l'ingestion sous quota exige des principes normatifs de respect du quota et de repli | §16 « API GitHub/GitLab limitée » ; REQ-SOC-04 ; §3.3 « artefacts CI » | mineure | Une exigence SHOULD : requêtes conditionnelles (ETag/If-Modified-Since), backoff exponentiel, pagination, et un mode fichier pour les collecteurs ; un test sans réseau |
| État de l'interface « **accès refusé** » alors que l'application est sans authentification ; quand ce niveau d'état s'affiche ? | §9.1 « États : chargement, vide, erreur, données périmées, accès refusé » ; §12 « aucune authentification » | mineure | Retirer l'état ou l'associer à une règle précise (ex. dépôt/projet désactivé) |
| **Agent ou CLI introuvable au lancement** : les prérequis (CLI installée, accès au modèle, config lue) ne sont pas vérifiés ; `doctor` couvre le serveur, pas le préflight d'un run | REQ-AGT-06 ; `sdlc-console doctor` (§9.3) | mineure | Préflight avant confirmation : vérification CLI, modèle, budget, dépôt, affichage de blocage explicite plutôt qu'un échec au premier lancement |
| Logs et erreurs d'ingestion : le format unique `{code, message, details}` est bon — conforme après vérification | §9.2 « Les erreurs suivent un format unique » | conforme | — |

## 4. Sécurité

| Constat | Référence | Gravité | Proposition |
|---|---|---|---|
| **Sans auth, CSRF est inopérant (pas de session/cookie) ; l'attaque réaliste est le DNS rebinding** vers `127.0.0.2` : un site distant peut POSTer vers `/api/projects/{id}/runs` et lancer un agent. La mitigation « CSRF token, SameSite » (§11) ne couvre rien dans ce modèle, et la validation d'origine n'est pas exigée | §11 lignes « API locale » et « CSRF » ; §3.2 « Authentification : aucune en MVP » | majeure | Exiger : validation **stricte de l'en-tête Host** (uniquement `127.0.0.2:8765` et localhost), refus des requêtes POST avec `Origin`/`Referer` externe ; requêtes JSON obligatoires (Content-Type) : un test de rebinding/DNS dans les contrôles sécurité |
| « `0.0.0.0` refusé » ne couvre pas toutes les expositions : `sdlc-console serve --host 192.168.1.10` n'est ni `0.0.0.0` ni loopback — le document annonce la limite de sécurité mais la règle est sous-spécifiée | §1, §12 « Écoute `127.0.0.2` », §10 « `0.0.0.0` refusé » ; §11 « Bind `127.0.0.2`, jamais `0.0.0.0` » | majeure | Reformuler : **tout bind non loopback (hors 127.0.0.0/8) est refusé**, message explicitant la règle « sans authentification → boucle locale uniquement » ; test paramétré sur `0.0.0.0`, `192.168.1.10`, `::`, `hostname` |

## Verdict

- Contestations bloquantes : 2
- Contestations majeures : 21
- Contestations mineures : 23

Les deux contestations bloquantes relèvent du processus, pas du contenu : décisions de conception structurantes sans ADR acceptés (gate « ADR acceptés » de l'étape 2 non passé) et absence des documents `exigences-nf.md` et brief validé (livrables de l'étape 1).
